## 1. Audit Methodology & Status Taxonomy

Every feature discovered across both commercial reference applications has been audited at the bytecode, resource, and manifest level, and evaluated against the Nothing Island codebase and Android 17 (API 37) platform boundaries.

### A. Status Classification (Strictly One per Requirement)
1. `IMPLEMENTED_AND_VERIFIED`: Fully built in Nothing Island, verified through unit tests (253 passing), and physically validated on the connected Nothing Phone (4a).
2. `IMPLEMENTED_NOT_PHYSICALLY_VERIFIED`: Fully implemented in source code and unit tested, but pending physical hardware interaction or environmental trigger.
3. `PARTIALLY_IMPLEMENTED`: Architectural foundation, DataStore models, or baseline logic exist, but specific interactions, variants, or edge cases remain incomplete.
4. `UI_ONLY`: Interface controls, sliders, or previews exist in Nothing Island Studio screens, but the underlying overlay renderer or system listener is not connected.
5. `MISSING`: Present in one or both reference applications, but not yet implemented in Nothing Island.
6. `BLOCKED_BY_ANDROID`: Platform permission restrictions, hidden API bans, or keyguard sandboxing on Android 17 prevent compliant implementation.
7. `REQUIRES_FURTHER_INVESTIGATION`: Identified in reference bytecode or assets, but requires deeper runtime tracing to establish operational mechanics.

### B. Android 17 Platform Feasibility Tiers
1. `Fully supported`: Supported natively through standard public Android 17 APIs without special user permissions or roles.
2. `Supported with user-granted permissions or special roles`: Feasible through public Android SDK APIs upon user runtime grant or special permission/role delegation (e.g. Notification Listener, Accessibility, Usage Access, Call Screening).
3. `Manufacturer-dependent`: Supported on standard hardware, but subject to OEM vendor variations or non-standard protocols (e.g. proprietary BLE battery protocols, vendor NPUs).
4. `Partially supported`: Certain aspects supported natively, while other components require launching system panels or alternative non-root flows.
5. `Requires elevated ADB permission (WRITE_SECURE_SETTINGS) / Experimental`: Functions that require elevated settings permissions not accessible via normal user runtime dialogues, such as global heads-up notification banner suppression (`REQ-90`).

### C. Visual Parity Strategy
- **Reference-Parity Mode (Default):** Full visual, motion, palette, and timing parity with the reference applications using independently authored, non-infringing assets and procedural shaders.
- **Nothing OS Native Tier (Optional Extras):** Dot-Matrix, monochrome, and Nothing Red styling provided as dedicated selectable options.

### D. Operational Connectivity Model: 100% Free & Ad-Free
- **Universal Policy: 100% Free & Ad-Free:** Every feature across both commercial reference applications—including all 34 VIP, premium, and coin-metered features—is provided completely free of charge, with zero paywalls, zero subscriptions, zero advertisements, and zero telemetry tracking libraries.
- **100% Offline-Capable (89 Requirements):** Overlay rendering, themes, animations, local notification processing, media transport, system events, gesture handling, telecom HUDs, quick settings panels, and standby clocks run completely locally on-device without internet access.
- **Network-Dependent Live Services (5 Requirements):** Features that inherently monitor or stream external network data: `REQ-58` (Download speed & progress tracker), `REQ-61` (Wi-Fi state transition), `REQ-83` (Live sports scores), `REQ-84` (Food delivery & ride-share tracker), and `REQ-95` (Weather live activity & 44 conditions).
- **Optional Cloud AI (1 Requirement):** `REQ-94` (AI Assistant defaults to a 100% offline, private on-device quantized model; optionally supports cloud AI reasoning if the user supplies an external API key).
